## 摘要

本文以「会记 · AI 会议纪要助手」为案例，记录在需求、分析、设计、编码、测试与文档全过程中应用 AI 模型完成一个小型应用系统的实践，并对开发过程进行分析评价。系统采用 Flask + SQLite + DeepSeek 构建，实现会议记录管理、AI 纪要提炼、待办跟踪、跨会议问答与 Word 导出。开发中由 AI 编程助手承担主要编码、测试生成与文档起草工作，开发者负责目标设定、范围裁剪、关键决策与验收。最终系统包含约 2600 行代码、32 个自动化测试，覆盖率 90%，真实模型联调完成「录入—提炼—问答—导出」闭环。报告重点分析 AI 在效率、质量与可维护性上的贡献，以及输出不确定性、幻觉、测试盲区与安全风险等局限，总结可复用的协作经验。

**关键词**：AI 辅助开发；大语言模型；会议纪要；DeepSeek；结构化输出；软件工程；过程评价

## 1 引言

### 1.1 背景

大语言模型已经能够理解自然语言、生成代码、编写测试与文档，正在改变软件开发的协作方式。但「让 AI 写代码」并不等于「完成一个可交付的系统」：需求是否清晰、架构是否合理、AI 输出是否可靠、测试是否有效，仍需要工程方法约束。本次作业要求基于 AI 模型完成小型应用系统并进行全过程评价，正是对这一问题的实践。

### 1.2 项目简介

「会记」面向工程项目建设中的会议场景。用户粘贴会议速记或录音转写文本后，系统调用 DeepSeek 生成摘要、决议与待办，支持待办跟踪、跨会议问答和 Word 导出。系统定位为本地单用户工具，数据保存在 SQLite，AI Key 仅存服务端 `.env`。

### 1.3 报告结构

第 2 章按阶段回顾开发过程；第 3 章分析 AI 在各阶段的作用与典型案例；第 4 章讨论问题与不足；第 5 章从效率、质量、可维护性等维度评价；第 6 章总结经验；第 7 章给出结论。

## 2 开发过程

### 2.1 总体流程

| 阶段 | AI 承担的工作 | 开发者承担的工作 | 主要产出 |
| --- | --- | --- | --- |
| 选题与需求 | 提供候选方案、分析可行性与规模 | 选择会议纪要方向、确定边界与优先级 | 需求规格说明书 |
| 系统分析 | 生成业务流程、用例、ER 图与数据流草案 | 检查业务一致性、确认关键流程 | 系统分析说明书 |
| 系统设计 | 提出架构、表结构、接口与提示词方案 | 确认技术选型、约束与安全取舍 | 系统设计说明书 |
| 编码 | 生成后端、模板、样式与交互代码 | 配置环境、审查代码、提出修改 | 可运行系统 |
| 测试 | 生成用例、假服务与测试脚本 | 设计测试策略、执行真实联调 | 32 个测试、联调记录 |
| 文档与发布 | 起草文档、生成截图、整理提交 | 确认内容、建立分支、推送仓库 | 文档、Git 历史 |

整个过程不是「一次生成即完成」，而是「AI 生成 → 运行/测试 → 反馈 → 修正」的循环。关键节点均由人做取舍，例如放弃工程项目管理与记账题目、限定为单用户本地工具、选择 SQLite 而非向量数据库。

### 2.2 需求阶段

需求阶段首先收敛题目。AI 曾提出工程项目管理、知识库问答、错题本、简历助手、记账助手等方案；由于记账系统此前已实现过，项目管理与既有仓库描述重复，最终选择「会议纪要助手」。这一选择基于三点判断：

1. AI 的能力与业务高度匹配：摘要、信息抽取、问答都是大模型的强项；
2. 系统边界清晰：会议、决议、待办、问答四类实体即可支撑完整闭环；
3. 可验证性好：待办是否提取正确、日期是否换算正确，可以量化检查。

随后将需求拆成 8 条功能需求与 7 条非功能需求，并为每条定义验收要点。例如「重新提炼保留已完成状态」「无 Key 时基础功能可用」「AI 失败不丢数据」等要求，后来直接影响了设计与测试。

### 2.3 分析阶段

分析阶段使用 AI 生成业务流程、用例、功能结构、ER 图与关键时序图草案，再由人检查：

- 待办状态是否应有「逾期」持久化状态？最终决定不落库，按截止日期实时计算，避免状态漂移；
- 问答来源是否要外键？最终决定以 JSON 快照保存，保证会议删除后历史问答仍可读；
- 检索是否需要向量库？考虑到数据量小、部署要轻，选择关键词打分 + 最近会议回退。

这一阶段的体会是：AI 很擅长把模糊描述转成结构化图表，但是否符合业务语义仍需人判断。例如「逾期」的处理方式，AI 初稿倾向于增加状态字段，人工分析后选择了派生状态。

### 2.4 设计阶段

设计阶段确定了分层结构与技术栈：

- **表现层**：Jinja2 + 原生 JS，不引入前端构建链；
- **控制层**：Flask 蓝图，负责校验、编排与事务；
- **服务层**：`AIService` 封装模型调用、JSON 解析与检索；`docx_export` 负责排版；
- **数据层**：SQLite，参数化查询，外键级联；
- **配置层**：`.env` 保存 Key、模型、超时，`.gitignore` 排除。

提示词与 JSON 契约也在设计阶段确定。提炼提示词明确「只依据原文、只输出 JSON、决议与讨论区分、相对日期换算、待办可执行」；问答提示词明确「只用资料、资料不足要说明、纯文本、标注来源」。这些约束不是一次写好的，而是在联调中发现模型使用 Markdown 后补充了「禁止 Markdown 标记」。

### 2.5 编码阶段

编码由 AI 生成首版，开发者负责环境准备、运行与验收。代码规模如下：

| 类别 | 文件数 | 行数（含空行/注释） |
| --- | --- | --- |
| Python 生产代码 | 6 | 1037 |
| 测试代码 | 3 | 556 |
| 模板 HTML | 6 | 407 |
| CSS / JS | 2 | 485 |
| SQL 与演示脚本 | 2 | 129 |
| **合计** | **19** | **约 2614** |

注：以上统计不含 Markdown 转 Word 的文档生成工具（约 460 行），该工具仅用于交付物排版。

实现顺序按依赖推进：配置与数据库 → AI 服务与解析 → 路由与模板 → 前端交互 → Word 导出 → 测试。每次生成后立即运行测试或启动页面，发现问题再让 AI 修改。

编码阶段发现并修复了两个典型问题：

1. **导航按钮样式被覆盖**：`.nav > a` 的灰色文字规则优先级高于 `.btn-primary`，导致顶部「新建会议」按钮对比度不足。该问题无法由单元测试发现，是通过无头浏览器截图验收才暴露的。
2. **问答输出含 Markdown**：模型返回 `**李敏**`，页面按纯文本渲染，用户会看到星号。修复方式不是前端加 Markdown 渲染（会引入 XSS 风险），而是在提示词中约束纯文本输出。

### 2.6 测试阶段

测试策略的核心是「测试与 AI 解耦」：

- 定义 `FakeAIService`，返回固定的摘要、决议与待办；
- 路由测试注入假服务，覆盖 CRUD、校验、提炼、状态保持、问答、导出与异常；
- 对 JSON 解析单独做单元测试，覆盖代码块围栏、前后噪声、字段缺失、多种日期写法；
- 真实 Key 只用于一次端到端联调，避免测试消耗额度与受网络波动影响。

最终结果：32 个用例全部通过，整体覆盖率 90%，其中 `ai_service.py` 71%、`routes.py` 89%、`docx_export.py` 98%。真实联调中，351 字记录在 6.7 秒内生成 3 条决议、5 条待办，「下周三」「本周五」等相对日期均换算正确；两次问答分别耗时 1.5 秒与 3.3 秒，来源标注正确；Word 导出 37 KB，内容与数据库一致。

### 2.7 文档与发布

文档包括需求规格、系统分析、系统设计、测试报告与本报告，均由 AI 起草、人工确认。Git 采用简化分支模型：

- `main`：稳定版本；
- `develop`：集成分支；
- `feature/core-app`：核心功能开发分支；
- `docs/report`、`docs/final-report`：文档与定稿分支。

提交按「初始化 → 数据库与 AI 封装 → 页面与导出 → 测试 → 合并」拆分，合并使用 `--no-ff` 保留分支轨迹，最终推送到 GitHub 仓库。

## 3 AI 应用分析

### 3.1 各阶段效果

| 阶段 | AI 贡献 | 效果评价 | 局限 |
| --- | --- | --- | --- |
| 需求 | 候选方案、需求条目、验收标准 | 快速打开思路，结构完整 | 容易扩大范围，需要人裁剪 |
| 分析 | 流程图、用例、ER 图、时序图 | 表达效率高，格式规范 | 业务语义需人工判断 |
| 设计 | 架构、表结构、接口、提示词 | 方案成熟，考虑较全 | 倾向使用更复杂的方案 |
| 编码 | 全部首版代码 | 速度快、风格统一 | 细节缺陷需运行/截图发现 |
| 测试 | 用例、假服务、断言 | 覆盖全面，回归成本低 | 假服务无法验证真实模型 |
| 文档 | 文档初稿、截图整理 | 显著节省时间 | 需要与实现核对，避免夸大 |

### 3.2 有效实践

**（1）用验收标准约束需求，而不是只写功能名。** 例如「AI 失败不丢数据」「重新提炼保留完成状态」这类可测试的表述，直接转化为测试用例与事务设计。

**（2）结构化输出 + 容错解析。** 仅靠提示词要求 JSON 不够，系统同时使用 JSON mode、代码块剥离、首尾花括号截取、字段归一化与空结果判定。真实模型输出质量较好，但设计上不能假设它永远正确。

**（3）把 AI 调用封装在服务层。** `AIService` 与路由解耦，测试可注入假服务，既保证测试稳定，也方便未来更换模型或供应商。

**（4）测试生成与测试策略分离。** AI 生成具体用例和断言，人决定「测什么、怎么隔离、哪些必须真实联调」。这是测试有效性的关键。

**（5）用截图做 UI 验收。** 样式优先级问题无法靠 pytest 发现，使用 Playwright + Edge 无头浏览器截图后才暴露。AI 可以生成截图脚本，但「看一眼截图」仍是人的工作。

**（6）小步提交与分支隔离。** 功能分支完成后再合并，提交粒度按模块拆分，便于回溯与审查。

### 3.3 典型案例

**案例一：相对日期换算。** 输入记录包含「下周三」「本周五」「本周内」「12 月 3 日」，会议日期为 2026-11-18。模型输出分别为 2026-11-25、2026-11-20、2026-11-20、2026-12-03，全部正确。这说明在提示词中提供会议日期并要求换算，可以显著提升结构化抽取质量。

**案例二：问答的来源标注。** 问题「省平台接口文档由谁负责跟进？什么时候完成？」的回答引用了正确的会议与日期，并说明待办状态为未完成。检索层先按关键词选出会议，再把摘要、决议、待办与原文摘录一起送入模型，减少了跨会议串扰。

**案例三：模型格式漂移。** 初期回答使用 Markdown 加粗，页面显示星号。修复选择在提示词层禁止 Markdown，而不是在前端渲染 Markdown。原因是会议原文可能包含恶意内容，渲染富文本会增加 XSS 面；纯文本策略更安全、更可控。

## 4 问题与不足

### 4.1 模型输出的不确定性

即使使用 JSON mode，模型仍可能返回代码块、前后说明或字段缺失。系统通过多层解析与校验降低风险，但无法保证 100% 成功。实际联调中未出现解析失败，但测试专门覆盖了这些情况，说明团队并不把「这次成功」当成「永远成功」。

### 4.2 幻觉与事实性风险

纪要提炼可能把讨论写成决议，或把未明确的人名写进负责人；问答可能在资料不足时给出看似合理的推断。系统通过提示词约束、来源标注与人工复核降低风险，但没有事实校验机制。对于正式会议纪要，AI 输出只能作为草稿。

### 4.3 对隐含需求不敏感

AI 能实现明确说出的需求，却不容易发现「按钮对比度不足」「长文本在移动端溢出」这类隐含质量要求。本次导航按钮问题就是通过截图才发现的。这说明 AI 辅助开发不能省略人工验收，尤其是 UI 与交互。

### 4.4 测试盲区

假 AI 服务让测试稳定，但也意味着真实模型的行为没有被自动化覆盖。本次采用「契约测试 + 一次真实联调」折中：契约测试保证解析与业务逻辑，联调验证端到端质量。真实模型的随机性、限流与网络异常仍需在生产使用中持续观察。

### 4.5 方案膨胀倾向

AI 容易提出更完整的方案，例如引入向量数据库、登录体系、消息队列等。这些方案在大型系统中合理，但会超出课程作业的范围。开发者需要持续裁剪，保持「小而完整」。本项目最终坚持 SQLite + 关键词检索 + 单用户，就是主动控制复杂度的结果。

### 4.6 安全与隐私

会议原文会发送给模型服务，可能包含敏感信息；提示词注入也可能让记录中的指令影响模型。当前系统通过「仅发送必要文本、Key 服务端保存、纯文本渲染、人工复核」降低风险，但未实现内容脱敏、注入检测与访问控制。若用于真实企业环境，需要补充这些能力。

### 4.7 过程管理挑战

AI 生成速度快，代码量迅速增加，审查负担随之上升。若不加控制，容易出现「能跑但难维护」的代码。本项目通过分层、配置外置、测试与文档来约束；同时用分支与提交粒度保留过程痕迹，避免一次性堆叠所有改动。

## 5 效果评价

### 5.1 效率

从确定题目到完成可运行系统、自动化测试、真实联调、文档与 GitHub 推送，整个过程在单个工作会话内完成（小时级）。传统方式下，同类系统通常需要数天到两周。效率提升主要来自：

- 样板代码（CRUD、模板、样式、测试夹具）几乎无需手写；
- 文档与图表初稿生成快；
- 测试用例可批量生成，回归成本低。

但这一数据来自单次实践，且系统规模较小，不能直接外推为普遍的生产力提升比例。

### 5.2 质量

- 32 个测试全部通过，覆盖率 90%，核心路由与导出模块覆盖充分；
- 真实联调输出质量较高，相对日期、负责人、截止日期均正确；
- 发现并修复 2 个产品缺陷，无阻断性问题；
- 代码分层清晰，配置与密钥管理符合基本安全要求。

质量提升的关键不是「AI 写得完美」，而是「AI 生成 + 自动化测试 + 人工验收」的组合。没有测试与截图验收，导航样式与 Markdown 污染很可能被遗漏。

### 5.3 可维护性

- `AIService`、`db`、`docx_export`、`routes` 职责分离；
- 模型、超时、数据库路径均可配置；
- 测试可离线运行，便于持续集成；
- 文档覆盖需求、分析、设计、测试与评价，形成闭环。

不足是前端仍为服务端渲染 + 原生 JS，交互复杂后维护成本会上升；数据层未使用迁移工具，表结构变更需要手工处理。

### 5.4 学习价值

本次实践最大的收获不是「学会了 Flask」，而是理解了 AI 辅助开发的边界：

1. AI 擅长把明确意图快速变成代码与文档；
2. AI 不擅长替人定义「什么算完成」，验收标准必须由人给出；
3. AI 的输出必须被验证，测试、运行、截图、真实联调缺一不可；
4. 安全与隐私不能交给模型判断，必须由工程约束兜底。

### 5.5 局限

本报告基于单个小型项目，缺少与传统开发方式的对照实验；AI 生成占比为估计值，未做代码溯源统计；模型输出质量受网络、模型版本与提示词影响，结果不保证可复现。这些局限不影响对过程的定性分析，但应避免过度概括。

## 6 经验与建议

1. **先定验收，再让 AI 写。** 把需求写成可测试的验收标准，AI 的输出才有明确目标。
2. **结构化输出要配合校验。** JSON schema、解析容错、字段归一化、空结果判定缺一不可。
3. **把 AI 关在接口后面。** 业务代码不直接依赖模型 SDK，测试才能稳定、替换才容易。
4. **假服务测逻辑，真实联调测质量。** 两者不能互相替代。
5. **UI 必须人看。** 自动化测试覆盖不了视觉与交互细节，截图验收成本低、收益高。
6. **主动裁剪范围。** AI 会倾向给出更完整的方案，开发者要守住项目边界。
7. **安全默认从严。** Key 不入库、页面纯文本渲染、默认监听本机、敏感内容先脱敏。
8. **保留过程痕迹。** 小步提交、功能分支、测试记录与联调数据，都是报告与复盘的依据。

## 7 结论

本项目以会议纪要助手为载体，完成了需求、分析、设计、编码、测试与文档的全流程 AI 辅助开发。AI 在代码生成、测试编写、文档起草与图表表达上显著提升了效率；开发者则在选题、范围、架构取舍、验收与安全约束上发挥不可替代的作用。最终系统功能完整、测试充分、真实联调可用，验证了「AI 作为高效实现者、人作为目标与质量守门人」的协作模式。

同时，实践也暴露了 AI 的局限：输出不确定、可能幻觉、对隐含质量不敏感、测试存在盲区、安全需人工兜底。因此，AI 辅助开发的核心不是「少写代码」，而是「把验证做得更系统」。只有将 AI 生成纳入需求、设计、测试与评审的工程闭环，才能真正把速度转化为可交付的质量。
